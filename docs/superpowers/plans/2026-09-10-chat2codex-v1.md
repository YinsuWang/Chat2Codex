# Chat2Codex V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an end-to-end local-first Chat2Codex V1 in which ChatGPT Chat plans, supplies code-level guidance, and reviews; a deterministic Supervisor binds state and workspaces; Codex CLI is the default code executor; and a Codex Desktop in-app-browser relay carries small control messages for the current Plus-compatible workflow.

**Architecture:** The system has three independent boundaries: a read-only MCP data plane, a durable Supervisor/control inbox-outbox, and a pluggable Codex execution adapter. ChatGPT never receives shell or project-write tools. The Supervisor validates workspace/task/base identity, creates an isolated Git worktree, launches `codex exec --json`, records primary evidence, and lets ChatGPT review that evidence through MCP.

**Tech Stack:** Node.js >= 20, TypeScript 5.9+, ESM, pnpm, `@modelcontextprotocol/sdk` 1.x, Zod 4.x, Express 5.x, Commander 14.x, Vitest 3.x, native `node:child_process`, native `node:fs/promises`, native `node:crypto`.

**Spec:** `docs/superpowers/specs/2026-09-10-chat2codex-v1-design.md` plus `docs/superpowers/specs/2026-09-10-chat2codex-v1-control-transport-amendment.md`

## Global Constraints

- ChatGPT is the planner, code designer, and independent reviewer; it must not receive arbitrary shell, project write, delete, commit, or push tools.
- Codex is the only component that performs project code writes and local execution.
- Supervisor is deterministic orchestration/state, not another reasoning agent.
- `guided` is the default implementation mode; `delegate` and `patch` are also valid.
- One registered `workspace_id` identifies exactly one machine-local canonical workspace root.
- Every control message carries `workspace_id`, `task_id`, and `iteration`.
- Git worktree isolation is the default; current-working-tree execution requires an explicit workspace policy.
- `EXECUTED` means an attempt finished, not that the code is correct.
- Review is based on actual diff/test/execution records, not Codex prose.
- The V1 automatic Plus-compatible UI relay is a Codex Desktop Skill using the built-in in-app browser; `codex exec` is not assumed to have browser control.
- Read-only MCP exposure must deny sensitive files and canonical-path escapes.
- No owned domain, inbound router forwarding, VPS, or fixed public IP is required by the core design.
- Do not add Electron, a dashboard, multi-user support, cloud execution, or automatic Git push in V1.

- [ ] **Step 4: Implement discriminated protocol types and Zod schemas**

```ts
export type ImplementationMode = "delegate" | "guided" | "patch";

export interface MessageIdentity {
  workspace_id: string;
  task_id: string;
  iteration: number;
}

export interface PlanMessage extends MessageIdentity {
  kind: "PLAN";
  implementation_mode: ImplementationMode;
  base_sha?: string;
  goal: string;
  instructions: string[];
  constraints: string[];
  acceptance_criteria: string[];
  patch?: string;
}

export interface ExecutedMessage extends MessageIdentity {
  kind: "EXECUTED";
  exit_code: number;
  changed_files: number;
  tests_summary: string;
}

export interface ReviewFinding {
  severity: "low" | "medium" | "high";
  file?: string;
  issue: string;
  required_change: string;
}

export interface ReviewMessage extends MessageIdentity {
  kind: "REVIEW";
  decision: "PASS" | "REVISE";
  findings: ReviewFinding[];
}

export interface DoneMessage extends MessageIdentity {
  kind: "DONE";
  summary: string;
}

export type ControlMessage = PlanMessage | ExecutedMessage | ReviewMessage | DoneMessage;
```

Use `z.discriminatedUnion("kind", ...)`; require non-empty IDs and `iteration >= 0`. For `patch` mode require a non-empty `patch` field with a `superRefine` check; disallow `patch` for other modes.

- [ ] **Step 1: Add protocol fixtures that the Skill must relay unchanged**

- [ ] **Step 2: Write the Skill's non-negotiable role rules**

The Skill must state:

```text
ChatGPT owns planning, code-level guidance, and review.
The Chat2Codex Supervisor owns task/workspace state.
CodexCLIAdapter owns project execution.
This Desktop session is the control relay: it must not reinterpret PLAN/REVIEW messages.
Never paste repository files, diffs, or logs into ChatGPT; ChatGPT reads those through MCP.
Only relay messages beginning with [CHAT2CODEX].
Use only the workspace connector named by chat2codex status.
```

- [ ] **Step 3: Define one-tab IAB behavior**

Mirror the proven C2C approach: initialize the built-in in-app browser once, reuse one ChatGPT tab, keep it available, use the saved chat/project URL, and never use an external browser for automated message exchange. The Skill must never assume `codex exec` has browser access.

- [ ] **Step 4: Define outbound relay loop**

The Skill repeatedly performs:

```text
chat2codex control next --workspace <id> --json
→ if no message, inspect current ChatGPT chat for a new [CHAT2CODEX] reply
→ if outbound message exists, send its formatted body to the bound chat
→ wait for ChatGPT generation to finish
→ read only the latest assistant [CHAT2CODEX] block
→ pipe it to chat2codex control ingest --workspace <id> --stdin
→ acknowledge the outbound envelope after successful send/ingest sequencing
```

Use cheap DOM checks at bounded intervals; do not resend an outbound message merely because one wait timed out.

- [ ] **Step 5: Define Chat-first task behavior**

The bound ChatGPT conversation's boot instructions tell ChatGPT that when the user asks for a code change it should inspect the workspace via MCP and emit a `PLAN` message. The Desktop relay must detect that assistant `PLAN` even when no preceding Supervisor outbound message exists, ingest it, and let Supervisor start the task. This is the key difference from a Codex-first-only workflow.

- [ ] **Step 6: Define post-execution review behavior**

After relaying `EXECUTED`, the Skill waits for ChatGPT to inspect `git_diff`, `execution_summary`, `test_status`, and optional readable `execution_output`. It then ingests either `REVIEW/PASS` or `REVIEW/REVISE`. It must not convert normal ChatGPT prose into a PASS implicitly.

- [ ] **Step 7: Document conversation boot contract**

`docs/protocol.md` must include a reusable boot instruction requiring `workspace_info` verification before planning, default mode `guided`, bounded control messages, and independent review.

## Implementation order and review gates

Implement strictly in task order. Tasks 1-3 establish identity/protocol/state; Tasks 4-6 establish safe local evidence and isolation; Tasks 7-9 establish execution/orchestration; Task 10 exposes review data; Task 11 adds the Plus-compatible Chat UI relay; Task 12 proves the full loop.

Each task is a review gate. Do not begin the next task until its focused tests, `pnpm typecheck`, and the task commit succeed.

## Self-review against the approved specs

- Workspace registration/binding: Tasks 2, 9, 12.
- Explicit workspace mismatch failure: Tasks 2, 9, 12.
- `delegate` / `guided` / `patch`: Tasks 1, 7, 11.
- Stale base guard: Tasks 5, 9, 12.
- Worktree default: Tasks 5, 9, 12.
- Codex CLI JSONL execution: Tasks 7, 9, 12.
- Persistent task/restart behavior: Tasks 3, 6, 9.
- Read-only MCP evidence plane: Tasks 4, 6, 10.
- Sensitive-file and path security: Tasks 4, 6, 10.
- Independent review from actual evidence: Tasks 6, 10, 11, 12.
- `PASS` / `REVISE` loop: Tasks 3, 9, 11, 12.
- Transport/executor separation from the amendment: Tasks 7, 8, 11.
- Chat-first initiation: Task 11 plus E2E Task 12.
- No direct ChatGPT shell/write authority: Tasks 4 and 10 enforce the tool boundary.
- No domain/VPS requirement in the core design: Task 10 keeps network exposure pluggable; Task 12 documents supported authenticated tunnel choices.

No V1 requirement is intentionally deferred except the amendment's explicit non-goal: fully automatic **CLI-only** ChatGPT UI relay without Codex Desktop. That capability requires a future `ControlTransport` implementation and does not block the approved Desktop-relay + CLI-executor V1 path.
